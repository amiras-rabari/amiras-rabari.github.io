Database from scratch

SQL goes in and rows come out. Everything in between is built by hand: the parser, the optimizer, the execution engine and the storage layer. No database libraries, parser generators or regular expressions.

View code on GitHub

How a query flows through it

  1. SQL textSELECT, JOIN, GROUP BY, ORDER BY, subqueries in FROM, UNION and friends.
  2. sqlHand-written lexer and recursive-descent parser, then name resolution and type checks. Errors point to the exact line and column.
  3. Logical plan (JSON)A tree of relational operators, the contract between modules.
  4. optStatistics with equi-depth histograms, selectivity estimates, seven rewrite rules, an I/O cost model and Selinger-style dynamic programming over join orders.
  5. Physical plan (JSON)Concrete algorithms chosen for the memory budget, such as hash join or sort-merge join.
  6. execVolcano-style open / next / close iterators: scans, filters, external sort, three joins, hash aggregation and set operations.
  7. storageA buffer pool with LRU and CLOCK replacement over heap files of slotted 4 KB pages on disk.

The constraint that shapes everything

The whole engine runs under a hard memory budget of B pages, as small as 4. At most B pages are in memory at any moment, including tuples held in C++ containers. Sort, hash and join operators spill to temporary files instead of growing.

Every operator also reports deterministic I/O counters. The same data, plan and budget produce identical counts on every run, and those counts are checked against the textbook cost formulas, such as 3(M+N) for Grace hash join.

Hard problems

  • Making leaks impossible. Page pins, frame reservations, temp files and parser depth are owned by small move-only RAII guards. An early return or exception can't leave a page pinned. Tests assert zero pinned frames and zero live temp files after every plan.
  • Surviving hostile input. A query nested 1,000 levels deep has to produce an error, not a stack overflow, in every later pass too. One shared tree-height budget, enforced while parsing, solved it.
  • I/O you can account for. Each operator snapshots the buffer pool's counters, so EXPLAIN ANALYZE shows where the I/O went at every node and how far off the optimizer's estimate was.
  • Cost model and executor agree. The optimizer's formulas and the executor's real counters are tested against each other. Any mismatch is treated as a bug in one of them.
  • SQL semantics that look right but aren't. SQL works on bags, not sets. GROUP BY with no keys over an empty table returns exactly one row. The engine gets these cases right, and results are compared with PostgreSQL.

Architecture

Five libraries with a strict one-way dependency graph: common, storage, exec, sql and opt. Each one works as a library and as its own command-line tool. A final shell wires them together without rewriting any of them, and supports CREATE, INSERT, LOAD, ANALYZE, EXPLAIN and EXPLAIN ANALYZE.
